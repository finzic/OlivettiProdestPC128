Introduction

It is unusual to worry about how a BASIC program is run by a computer.

The latter, however, is only able to directly execute quite elementary instructions, much less complex than a FOR or IF or other BOXF...

We are therefore interested in this book with the interpreter, i.e. the program responsible for decoding and executing instructions written in BASIC.

We have chosen for this the very widespread version 5.0 of the company MICROSOFT, written here for two microcomputers THOMSON TO7 and 707-70 and their microprocessor 6809.

After having presented in a first part the two TO7 and studied in detail the programming of the 6809, ja second part allows to understand / operation of the interpreter, common to the two TO7.

The other two parts of this book are then devoted to applications, consisting first of modifying and completing the original BASIC and then improving its performance.

The two computers TO7 and TO7-7@, which appeared in late 82 and mid 84 respectively, are perfectly representative of what can be expected today from family computing.

For example:

SWI instruction

It allows for software interruptions; It is therefore most often used to make address stops for program development.

WHILE... WEND

The two WHILE and WEND instructions allow you to loop on a sequence of instructions as long as a certain condition, written after the WHILE, is fulfilled: when it is no longer so, there is a connection to the instruction following the WEND.

This makes it possible to make loops different from those controlled by FOR and NEXT: their main interest is to allow a good structuring of the programmes, this concept being as is known to be fundamental in programming: it greatly facilitates the writing, development and subsequent modifications of a programme.

It should also be noted that the possibility of writing sub-programs with local variables, as discussed in Chapter VI, is another very important element of structured programming.

I. Principle of creating a WHILE loop

The corresponding routine, which is similar in principle to that of a FOR loop, uses the $16AC routine, which in all cases finds the WEND associated with WHILE (see Part 2).

When treating WHILE, we then suckly stack: — the address of the character following WHILE,

— the number of the WHILE line (both of which can be repositioned when the WEND returns),

— the address of the character following the associated WEND,

— the &HAF value, i.e. the WHILE code {this makes our routine compatible with the $2F3 routine, called by FOR and GOSUB).

It is then called the WEND treatment routine, which tests the condition; So your loop will only be executed if it is true.

The treatment of WEND consists essentially of testing the loop control condition:

— if it is true, we reposition ourselves at the beginning of the loop and we make a
JMP $2AED                ; which causes the execution of the corresponding instructions
(see Part 2),

— If it's wrong, you stay positioned after the WEND, you depilate the 7 bytes stacked by the WHILE and you still make JMP $2AED.

Finally, the two WHILE and WEND routines will be activated by an initialization sub-program that modifies $6233 (WHILE) and $6236 (WEND), initially containing a JMP $7F3 (SN Error) instruction corresponding to WHILE and WEND processing.

Local variable procedures

It is known that the most effective method for dealing with a complex problem is to break it down into several independent sub-problems: each sub-problem can itself be broken down in the same way into ‘sub-sub-problems', etc... until there are basic problems that can be programmed immediately.

This method of analysis ‘by gradual refinement' is referred to as ‘descending'; It therefore operates from general to retail, not in the opposite direction as is unfortunately commonly done.

Such an approach is possible in BASIC (use of GOSUB and not GOTO...} even if this language is not suitable for this; However, the information used by all the other programme units must be taken into account at each level; it is therefore not possible to write and develop each module independently of the others, hence the practical impossibility of writing and developing long programs, and the difficulty of finding certain errors leading to anarchic behaviors

This is due to the fact that in BASIC all variables in a program are common to all parts of it, thus leading to interac-

harmful ; the only exception is made for some BASIC by FN user functions, limited to a simple calculation and therefore without actual scope.

We give here a method for creating programme units, or procedures, independent of each other: all the information used by one of our procedures has meaning only for it, i.e. it is /oca/es to the procedure.

I. Method principle — Arguments passage

1. Principle

The second part saw that the interpreter manages the information used by a program from the addresses contained in $611E (early variable zone), $612@ (early table area) and $6122 (early DEB of the free zone, containing the stack).

To create local variables or arrays to a certain part of the program, simply send the DEB address in $611E and $6129, after saving the initial values in the stack.

All variables or arrays encountered then will be automatically created (by routine $448) in a memory area independent of the normal area, and will therefore be completely different from the variables or arrays used so far, even if the names are the same!

Of course, the values of $611E, $612@ and $6122 (the latter with the content of $611E, which does not move) will be restored upon return to the main program (PROCEND statement defined below); The information used by the procedure will therefore not be "seen" by the programme which calls it.

2. Crossing arguments

It is obvious that a procedure cannot be an isolated block, unrelated to other program modules; it must therefore be able to receive and return information; This is the problem of passing arguments.

It is therefore necessary to specify at the time of the appeal of the procedure (CALL instruction) the list of arguments, or parameters, to be transmitted to the procedure (effective arguments).

When defining the procedure (PROC instruction), the list of formal arguments will be written, receiving the values of the actual parameters.

There are essentially two traditional methods of passing arguments; Our instructions actually allow the use of both modes.

— Crossing by value: it is then simply the values of the actual parameters which are transmitted to the procedure: we ‘recopy the values of these values after possible conversion in case of different types, in the corresponding formal variables.

The values and headers of an array are copied directly into the formal array, which will be automatically created with the same structure as the actual array; the name will have to be of the same type as this one, because it would be too long to execute to convert all the elements of the table one by one.

This mode is the passage of default arguments that we have chosen for our instructions, similar to the corresponding PASCAL instructions, to 

In this mode of passage, no value is returned to the main program, which is therefore totally protected from the treatments performed in the procedure.

— Passage by address: the address of the actual argument is then transmitted to the sub-program during the call; When returning to the main program, the values of the formal parameters are returned to the main program, i.e. the actual parameters are changed.

Note that this mode of passage is the normal mode of passage of FORTRAN; in PASCAL, the principle is the same as here (use of the VAR keyword); However, this declaration must be made when defining the procedure and therefore frozen once and for all.

The point of making the statement at the time of the call is that the procedure may not return the same parameters (and therefore not always modify the same effective parameters) in two different calls: see the example of the game of tokens given below.

Sprites

A mobile programmable graphic pattern on the screen is referred to as "sprite".

The movement always takes place without changing or erasing fa scene, i.e. everything happens as if the sprite passed in front of the decor; all encounters with fixed objects of the scene or with other sprites are detected automatically.

The use of sprites therefore greatly facilitates the writing of graphic animation programs; It also allows quality animations: fully programmable shapes and colors, continuous movements at any speed, etc...

The management of sprites is practically always carried out by a specialized circuit; this one does not exist on TO7, we present here an entirely software method, presenting itself as a routine of 349 bytes; It allows the animation of any number of different sprites, chosen here of size 16 x 16 points (easily editable).

PERFORMANCE

We have seen in the 2nd part that at each encounter by the interpreter of a variable or table name, there is a corresponding 

The same applies to plug-in labels, recalculated and searched for in the program each time.

This obviously results in a drop in performance compared to a compiler, where all this work (and all machine language translation) is performed once and for all, prior to execution,

On the other hand, this method of processing allows an extremely flexible and pleasant work "conversational", since the modifications of a programme being developed are taken into account immediately, obviously impossible with a compiler.

However, as a program has been developed, it becomes completely unnecessary to benefit from your previous opportunity.

149

We therefore propose a method to compile the addresses of the variables, as well as the connections and values of the constants as they are executed.

Our method automatically operates from the normal written program, and it is in principle in this form that it will be stored on tape or diskette; the compilation is implemented only after the implementation of an initialization subprogramme, the programme can of course be modified at will previously.

It is therefore apparent that the constraints of this "interactive" compilation are minimal; the result is a nearly doubled speed of execution.

Any application that turns around will therefore see its performance greatly improved by the application of our method, implemented by a simple EXEC written at the beginning of the program,

We will also discuss in this part the adaptation (always possible) of this method to other microcomputers than TO7.

Changing keyboard operation

All games operating in real time are presented in the form of a loop, in which one reads the keyboard or game controllers: depending on the result of the play, an action (moving an object for example} is performed and its consequences analyzed (collision or not...}, after which there is return to the beginning of the loop.

The keyboard of the TO7s is unfortunately very poorly adapted to this type of operation since in case of continuous appulsation on a key, there is constantly decoding of it, which causes each time a delay and the emission of a sound  This is unpleasant, and especially slows down the program.

We will see that it is easy to remove this disadvantage, from the observations of the second part. I. Removal of keyboard action

This does not solve our problem, since there is always decoding of supported keys and delaying, hence very sensitive slowing of execution.

Traditional revenue to improve performance

By following the few tips given here, one will be able to increase significantly the speed of implementation of a programme, usually from about 19 to 15%.

1. Write at the beginning of the program the most commonly used variables, if they affect a value (not by writing them in a calculation: see 2nd part): they will be created at the beginning of the variables area, and therefore found faster at each use.

2. Use input variables (DEFINT definition) whenever possible; the calculations are then much simpler, and therefore faster.

3. Use the INC statement in Part 3 for all X=X+expression calculations.

Interactive compilation of variable addresses and constants

When the interpreter encounters a variable in the program, he searches for it in the corresponding area, located just after the program itself: if he does not find it there, the variable is added at the end of the area, after moving the table area (this in the case of an assignment or a FOR, etc.).

It can be inferred that a variable created in memory is never moved during execution, whatever its type (digital or string).

From this observation we will see that it is possible to "courtcircult" the $A48 routine of looking for a variable; This will lead to a much clearer improvement in performance than can be achieved only by previous means.

I. The method

1. Principle

When the interpreter encounters a variable name, we replace in the program itself the variable name with its address; It is therefore automatically compiled during the first execution of the corresponding instruction.

When the interpreter then passes over the same statement (in the case of a loop), it can then go directly to the corresponding value, without any search.

2. Precautions to observe

With an address coded on 2 octats, the compilation can only be effective if the variable name has at least two characters, or a character followed by a space: moving the end of the program to add a space would indeed move the variables, making the addresses already compiled false.

On the other hand, we saw that we could not place in the program itself the values &H9,22.3A,89 and FF (because of the $66B routine seeking the end of an instruction, and used by GOTO,IF,FOR, etc...), or &HE8F81,8FAF,C481, etc... (routine $16AD used by FOR AND WHILE).

It is obvious that you cannot write as the first byte of an address a value corresponding to an instruction code: for example after a THEN, an address $8Qxx would be interpreted as a THEN END instruction, hence the program shutdown!

Finally, the interpreter should be able to distinguish an address (already compiled) from a variable name not yet compiled, which always starts with an byte containing a value from &H41(A) to &H5A({Z) {the variable ds names are indeed always encoded in capitals, even if they are written in tinys}; An address should not be confused with a constant, or parenthesis, etc...

Finally, the first byte of a compiled address can only be understood between &H5D and &H7F; The values below &H29 will be used for the compilation of constants.
